# Working on the Leichhardt Kitchen Book

The Kitchen Book is the Leichhardt Hotel kitchen's web app: the recipe book, the prep list, the order list, the wastage log, the transfer list (stock shared with the other venues), the team's how-to guides and the head chef's admin panel. Plain HTML, CSS and JavaScript on GitHub Pages, no build step. Live at https://kuschikuschbert.github.io/leichhardt-kitchen/.

## Never in this repo (it is public)
- The kitchen PIN and the owner's email. `firestore.rules` is a template with `KITCHEN_PIN` and `OWNER_EMAIL`; the real values only live in the published rules in the Firebase console.
- Prices, GP, supplier codes or anything else from AVC Live beyond ingredient names and quantities. AVC Live itself is read only: never change it.
- Staff names or PINs (they live in Firestore).

## Writing style (everything the team sees, and the code comments)
- No em dashes anywhere. Australian English, metric units, 24-hour time, Celsius, Australian kitchen terms.
- Plain, short sentences. Staff read this on the line.
- Only recipes, quantities, temperatures and times the head chef confirmed. Anything else goes in `[square brackets]` and shows as "To come".
- Times in messages to the head chef are Queensland time (Rockhampton, UTC+10, no daylight saving), 24-hour: "21:52", not "11:52 UTC". GitHub, workflow runs and tools report UTC, so add 10 hours before saying a time.

## Ground rules (no exceptions)
These hold for every session, every message and every change, however small. A hook in `.claude/settings.json` (`scripts/guard-main.mjs`) refuses edits and commits on `main`, so a session that skips them is stopped.

1. **Every interaction starts on a new branch.** Before touching a file, make a worktree on a fresh branch from the latest `main`:
   `git fetch origin main && git worktree add -b <type>/<short-name> .claude/worktrees/<short-name> origin/main`
   and work only in that folder. Never edit in the main checkout, never commit to `main`, never push `main`. One theme per worktree, branch and pull request: unrelated changes get their own worktree. A session that already has a worktree keeps it for that theme only. A cloud session that is given a branch to work on (`ccr-...`) uses that branch instead of a new worktree, started from the latest `main`; everything else here still holds.
2. **Check what else is in flight before merging.** Run `scripts/pre-merge.sh` from the worktree. It lists the open pull requests with their state, every worktree with its branch and uncommitted changes, and whether `main` moved since the branch started. Only one merge at a time: if another branch is ready or merging, wait for it, pull the new `main` into your branch, run the tests again, then merge. Never remove or reset a worktree that is not yours.
3. **Clean handoffs.** A branch is handed over only when it is pushed, has a pull request that says what was done and what is left, the tests pass, and `README.md` is in step. After a squash merge: `git -C "<main checkout>" pull --ff-only origin main`, remove the worktree and delete the branch. Nothing is left half done on `main`, and nothing lives only in a worktree.

## How changes ship
1. Start as above: a worktree on its own branch from the latest `main`.
2. Test before merging: `node --check` on changed JS, then `cd tests && npm install && npm test`. It serves the repo locally and runs every file in `tests/` in Chrome: each page at 390, 768 and 1280 px (no sideways scroll, no JS errors) and the click paths for the prep pages, orders, wastage, minutes, admin and recipe search. Firebase is replaced by the stand-in in `tests/fake/`, so no real PIN or data is needed and nothing is written to the real book. In a cloud session, where Google Chrome is not installed, run them with `CHROME=/opt/pw-browsers/chromium_headless_shell-1194/chrome-linux/headless_shell npm test` (the full Chromium there no longer runs headless the way the tests start it). Add checks for the click paths you change to the matching `*.test.js` file (or a new one). The same tests run on GitHub on every pull request to `main` (the **Click tests** check, `.github/workflows/pr-tests.yml`); a pull request does not merge until it is green. After merging, `BASE=https://kuschikuschbert.github.io/leichhardt-kitchen/ npm test` runs the same tests on the live site.
3. If `firestore.rules` changes: test it on the Firestore emulator first (`cd tests/rules && npm install && npm test`, and add a check for every new rule), publish it with the **Publish rules** workflow in the Actions tab (Run workflow; it fills the `KITCHEN_PIN` and `OWNER_EMAIL` secrets into a copy and deploys it with the service account), or from your own computer with `scripts/publish-rules.sh`, then merge the code that needs it. Publish rules before code that writes new fields or collections; publish after code when the rules get stricter about something old code does not send.
4. After merging, wait for GitHub Pages (about a minute), then check the live site. The **Live click tests** workflow runs the click tests against the live site by itself after each Pages deploy (and from the Actions tab); read its result.
5. Keep `README.md` in step with every change.
6. Before merging, run `scripts/pre-merge.sh` and follow the ground rules above.
7. **Claude merges, without asking** (head chef, 21 Oct 2026). Once the **Click tests** check is green, `scripts/pre-merge.sh` shows nothing else merging and `README.md` is in step, squash merge the pull request, then do step 4 and report the live result. This covers every change, rules and data included; the publish order in step 3 still applies. Ask only when something is genuinely the head chef's call (a recipe amount not confirmed, a choice between two behaviours), not to get permission to merge.

## Commits and pull requests
- The title says what changes for the team, in plain words: "Recipes opens faster and taps answer at once", not "Refactor backHome".
- The body says why first, with measured numbers when there are any (times, sizes, counts), then one line per file or part changed, then the tests added or changed.
- Same writing style as everything else: no em dashes, short sentences.
- `.github/pull_request_template.md` holds the sections every pull request fills in (why, what changes for the team, files, tests, reads and rules, rollback). Open work in progress as a draft.
- Branch names: `feat/`, `fix/`, `docs/`, `ci/`, `ux/` plus a short name, or the `claude/...` name the app gives a session. One owner per worktree: a session works only in the worktree it made or was given.

## Rollback, dependencies and secrets
- **Undo a bad merge** with `git revert <merge commit>` on a new branch and its own pull request, never a force push to `main`. Pages redeploys in about a minute and every phone picks the old code up through the update check (README, Good to know). Saved data is not rolled back by a revert: if the change wrote new fields, say in the pull request whether old code ignores them.
- **Rules roll back** by publishing the previous `firestore.rules` from `main` with the **Publish rules** workflow, then running the **Lock probe**.
- **Big look changes** keep a baseline first: a git tag on `main` (like `usability-baseline-2026-10-20`) and `tests/shots-baseline*/` (ignored by git), so the old look can be compared and restored.
- **Dependencies:** the book itself has none to install. Only `tests/` and `tests/rules/` have a `package.json`; change a version there in its own pull request with the full test run. A new outside script, font or service also needs the security header in `index.html` and is a head chef decision.
- **Secrets** (`FIREBASE_SA`, `KITCHEN_PIN`, `OWNER_EMAIL`, `BACKUP_KEY`) live only in GitHub Actions secrets and the Firebase console. Never print them in a workflow log, a test, a screenshot or a pull request.
- **Audit notes with security findings** stay out of this public repo: keep them untracked in their worktree or in a private artifact, and put only the fixes in pull requests.

## What GitHub enforces (checked 22 Oct 2026)
- `main` is protected: the **Click tests** check must pass and the branch must be up to date with `main`; force pushes and deleting `main` are refused.
- Not enforced by GitHub: reviews (none required, Claude merges by the head chef's decision of 21 Oct 2026), and the protection does not apply to admins. ## Things that are easy to break
- `.rail` is the steel shelf rail on the Pass; the landing and top bar use `.wtop`. Do not reuse class names across features (check `css/app.css` first).
- Shelves (`.shelf`) and tile groups (`.tile-group`) use `content-visibility: auto`, so a plate in a group off screen has no true position until it is drawn. Coming back to Recipes goes through `backHome()` in `js/app.js` (draws every group once, puts the opened plate back, then skips again). Anything new that measures or scrolls to a plate in those lists needs the same. The tap feedback uses the `scale` property inside `:where()`, so it never fights a part's own `transform` or `transition`; do not switch it to `transform`.
- Every write goes through `W()` in `js/prep.js`, which adds the writer's id (`by`). The rules check that phone's PIN session (`sessions/<uid>`, 22 Oct 2026; since phase 2 nothing else, see README, Staff lock), and a write made while a session is being opened waits for it (`sessP`). Direct `setDoc` calls bypass the staff lock and are refused. To ask whether this phone may write as the person signed in, use `canW()`, never `S.tok` (a phone that opened with its session has no PIN fingerprint in hand). PIN tries are one every 20 seconds per person (rules), so a test that types two PINs for one person runs the clock on 21 seconds between them; the test phones start with a running session (`tests/lib.js`, `o.oldTok` for the older proof).
- The prep pages read Firestore; keep reads small (the free plan has a daily read limit). Past days are cached once a day per phone with `dayCache()` / `lk.past` (prep, order history, the wastage summary, the waste review note); Everything to order is patched on the phone after a tick, not read again. Do not add polling.

## Coding rules (22 Oct 2026)
These hold for every file, old and new. When you touch code that breaks one, bring that code in line in the same branch if it is small, otherwise add it to "Bringing the code in line" in `README.md`. Older code that breaks a rule is listed there, so do not copy it as a pattern. One helper per job: use the one that exists (`esc()`, `W()`, `dayCache()`, `lvHTML()`, `now()`, `dayNow()`, `LK_RX.clean()`), never write a second.

**Reads (the free plan stops the book for the day at 50,000 reads)**
- Every new read says in a comment when it runs and what it costs: on open, once a day, after 30 minutes, or on a tap, and how many reads.
- No reads in a loop. Read many records in one query (`in` with up to 30 ids, a date range, or `collectionGroup`), never one `getDoc` per item or one `getDocs` per day. An empty collection still costs a read.
- A listener (`onSnapshot`) is only for today's live data that other phones change during service (today's prep, orders and wastage lines, `config/main`, the function list). Anything that changes overnight or rarely is read once a day and kept with `dayCache()`.
- A once-a-day job keeps its "done today" flag on the phone (`lk.*`), not only in memory, so the 04:00 refresh and updates do not run it again.
- Admin reports keep past days on the phone for the day and read only today fresh (`pastRead()` in `js/prep.js`). Refresh is a tap, never a timer.
- Totals that every phone needs from many past days (what is usual, what is wasted often) are worked out by the nightly job into one small record that phones read once a day.
- `tests/read-budget.test.js` sets a read budget for a staff phone's first open of the day, a reload, the admin panel and the admin panel again the same day (the stand-in in `tests/fake/` bills reads like Firestore: `__fake.bill`). A change that goes over it either reads less or raises the budget in the same pull request with the reason.

**Saved copies on the phone**
- Every saved copy (`lk.*`, IndexedDB) says in a comment what makes it out of date.
- A change to a past day must reach the saved copies on other phones too, not only the phone that made it: call `markPast('p' | 'o', date)` after the write, and have the saved copy check `pastStamp()` before it is used.
- A copy is saved only when every part came in. A failed read is never saved as "nothing there".

**Who sees what**
- Anything staff must not see is locked in `firestore.rules`, not only hidden on screen. Hidden-only is a bug.
- Staff pages show today. Past days, totals and corrections live in the admin panel for the head chef and sous chefs.
- Staff phones do not read past lines just to build hints: the hints come from the nightly summaries.

**Text on screen**
- Everything typed by a person or read from Firestore goes through `esc()` before it goes into HTML, attributes included.
- A value from Firestore placed in a `style`, an SVG attribute or a URL is checked by type first: a number in range, a colour (`#rgb`, `#rrggbb` or a named colour), or one of a fixed list. Never put it in as it came.
- SVG from Firestore or IndexedDB goes through `LK_RX.clean()` every time it is drawn, including copies kept on the phone.
- Links are fixed `#/` routes or use `encodeURIComponent`. No `eval`, `new Function` or string timers.
- `tests/safe-text.test.js` seeds a booby-trapped line into every kind of record others see and checks each page shows the words and adds no markup. A new field that others see gets a line there.

**Forms**
- Fill in what the book already knows (section, unit, reason, the usual amount), and keep it easy to change: the filled box is selected on tap, so typing replaces it.
- A suggestion chip fills every field it knows, not just the name.

**Screens**
- Every popup or sheet dims the page behind it, closes on the backdrop, Cancel and Escape, and is appended to `document.body`.
- A choice of more than about 12 things gets a type-to-find box with the likely few first, not a long dropdown.
- A row that scrolls sideways fades at its edge so people can see there is more.
- Group with space and headings first. A box or a fill is for something that needs attention, not for every group.
- Pages work at 390, 768 and 1280 px with no sideways scroll (the click tests check it).

**Loading**
- The book's start loads only what the landing page and the prep pages need. Anything big that only one page uses is loaded by that page (the loader `mountManage()` uses), and stays in `SHELL` if the book needs it with no signal.
- `js/art.js` is the exception, measured on 22 Oct 2026: loading it later saved 9 ms at the start and cost 90 ms on Recipes (README, Bringing the code in line). Measure before moving anything else out of the start.
