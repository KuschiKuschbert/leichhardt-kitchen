# Working on the Leichhardt Kitchen Book

The Kitchen Book is the Leichhardt Hotel kitchen's web app: the recipe book, the prep list, the order list, the wastage log, the team's how-to guides and the head chef's admin panel. Plain HTML, CSS and JavaScript on GitHub Pages, no build step. Live at https://kuschikuschbert.github.io/leichhardt-kitchen/.

## Never in this repo (it is public)
- The kitchen PIN and the owner's email. `firestore.rules` is a template with `KITCHEN_PIN` and `OWNER_EMAIL`; the real values only live in the published rules in the Firebase console.
- Prices, GP, supplier codes or anything else from AVC Live beyond ingredient names and quantities. AVC Live itself is read only: never change it.
- Staff names or PINs (they live in Firestore).

## Writing style (everything the team sees, and the code comments)
- No em dashes anywhere. Australian English, metric units, 24-hour time, Celsius, Australian kitchen terms.
- Plain, short sentences. Staff read this on the line.
- Only recipes, quantities, temperatures and times the head chef confirmed. Anything else goes in `[square brackets]` and shows as "To come".

## Ground rules (no exceptions)
These hold for every session, every message and every change, however small. A hook in `.claude/settings.json` (`scripts/guard-main.mjs`) refuses edits and commits on `main`, so a session that skips them is stopped.

1. **Every interaction starts on a new branch.** Before touching a file, make a worktree on a fresh branch from the latest `main`:
   `git fetch origin main && git worktree add -b <type>/<short-name> .claude/worktrees/<short-name> origin/main`
   and work only in that folder. Never edit in the main checkout, never commit to `main`, never push `main`. One theme per worktree, branch and pull request: unrelated changes get their own worktree. A session that already has a worktree keeps it for that theme only. A cloud session that is given a branch to work on (`ccr-...`) uses that branch instead of a new worktree, started from the latest `main`; everything else here still holds.
2. **Check what else is in flight before merging.** Run `scripts/pre-merge.sh` from the worktree. It lists the open pull requests with their state, every worktree with its branch and uncommitted changes, and whether `main` moved since the branch started. Only one merge at a time: if another branch is ready or merging, wait for it, pull the new `main` into your branch, run the tests again, then merge. Never remove or reset a worktree that is not yours.
3. **Clean handoffs.** A branch is handed over only when it is pushed, has a pull request that says what was done and what is left, the tests pass, and `README.md` is in step. After a squash merge: `git -C "<main checkout>" pull --ff-only origin main`, remove the worktree and delete the branch. Nothing is left half done on `main`, and nothing lives only in a worktree.

## How changes ship
1. Start as above: a worktree on its own branch from the latest `main`.
2. Test before merging: `node --check` on changed JS, then `cd tests && npm install && npm test`. It serves the repo locally and runs every file in `tests/` in Chrome: each page at 390, 768 and 1280 px (no sideways scroll, no JS errors) and the click paths for the prep pages, orders, wastage, minutes, admin and recipe search. Firebase is replaced by the stand-in in `tests/fake/`, so no real PIN or data is needed and nothing is written to the real book. In a cloud session, where Google Chrome is not installed, run them with `CHROME=/opt/pw-browsers/chromium_headless_shell-1194/chrome-linux/headless_shell npm test` (the full Chromium there no longer runs headless the way the tests start it). Add checks for the click paths you change to the matching `*.test.js` file (or a new one). The same tests run on GitHub on every pull request to `main` (the **Click tests** check, `.github/workflows/pr-tests.yml`); a pull request does not merge until it is green. After merging, `BASE=https://kuschikuschbert.github.io/leichhardt-kitchen/ npm test` runs the same tests on the live site.
3. If `firestore.rules` changes: test it on the Firestore emulator first (`cd tests/rules && npm install && npm test`, and add a check for every new rule), publish it with the **Publish rules** workflow in the Actions tab (Run workflow; it fills the `KITCHEN_PIN` and `OWNER_EMAIL` secrets into a copy and deploys it with the service account), or from your own computer with `scripts/publish-rules.sh`, then merge the code that needs it. Publish rules before code that writes new fields or collections; publish after code when the rules get stricter about something old code does not send.
4. After merging, wait for GitHub Pages (about a minute), then check the live site. The **Live click tests** workflow runs the click tests against the live site by itself after each Pages deploy (and from the Actions tab); read its result.
5. Keep `README.md` in step with every change.
6. Before merging, run `scripts/pre-merge.sh` and follow the ground rules above.
7. **Claude merges, without asking** (head chef, 21 Oct 2026). Once the **Click tests** check is green, `scripts/pre-merge.sh` shows nothing else merging and `README.md` is in step, squash merge the pull request, then do step 4 and report the live result. This covers every change, rules and data included; the publish order in step 3 still applies. Ask only when something is genuinely the head chef's call (a recipe amount not confirmed, a choice between two behaviours), not to get permission to merge.

## Commits and pull requests
- The title says what changes for the team, in plain words: "Recipes opens faster and taps answer at once", not "Refactor backHome".
- The body says why first, with measured numbers when there are any (times, sizes, counts), then one line per file or part changed, then the tests added or changed.
- Same writing style as everything else: no em dashes, short sentences.

## Things that are easy to break
- `.rail` is the steel shelf rail on the Pass; the landing and top bar use `.wtop`. Do not reuse class names across features (check `css/app.css` first).
- Shelves (`.shelf`) and tile groups (`.tile-group`) use `content-visibility: auto`, so a plate in a group off screen has no true position until it is drawn. Coming back to Recipes goes through `backHome()` in `js/app.js` (draws every group once, puts the opened plate back, then skips again). Anything new that measures or scrolls to a plate in those lists needs the same. The tap feedback uses the `scale` property inside `:where()`, so it never fights a part's own `transform` or `transition`; do not switch it to `transform`.
- Every write goes through `W()` in `js/prep.js`, which adds the writer's id (`by`) and the PIN proof with a server timestamp. Direct `setDoc` calls bypass the staff lock and are refused.
- The prep pages read Firestore; keep reads small (the free plan has a daily read limit). Past days are cached once a day per phone with `dayCache()` / `lk.past` (prep, order history, recent waste, the waste review note); Everything to order is patched on the phone after a tick, not read again. Do not add polling.
- The shift pings popup (called notes in the code and the data) is appended to `document.body`, not `#app`, so page redraws do not remove it. Its clicks use `data-note` (the bell and the popup), the editor inside the prep root uses `data-p`, and the recipe pages use `data-act`; keep them apart. Pings are read with one small query when the book opens each day, and again only after 30 minutes away or at 10:30 if the book was already open: do not add a listener or polling. Only the head chef and sous chefs write them: the rules check `sousIds` or `pingIds` in `config/main`, both the same people now (kept in step by the admin panel, `seedIds()`, which asks the head chef first when a sous chef changed a role); a sous chef's save sends only `people` and `staffIds` (who may set a PIN).
- Meeting minutes follow the same pattern (one small query, refreshed after 30 minutes away), clicks via `data-p` / `data-k` with `mn-` names. Minutes to sign show as the "Minutes not signed yet" card on the landing page (`.wall-mn`, an empty slot drawn by `js/app.js` and filled in by `minCard()` in `js/prep.js`) and on the prep list, not in the top bar. The chef mark's menu (`whoMenuOpen()` in `js/app.js`, `chefMenu()` / `chefOpen()` / `signOutPerson()` in `js/prep.js`) holds Meeting minutes, the drinks run, the Chef group (Admin panel, Shift pings, Minutes register, Manage staff), Settings and Sign out; the open mail count sits on the chef hat. Handy has no Tools and nothing prints or shares. Keep the top bar to Pings and the chef hat: one more button there pushes "Kitchen Book" onto two lines on a laptop. The chef mark (`.wtop-who`, a ring shown while a person is signed in) shows its name from 1400 px only; with the name at 1280 px "Kitchen Book" wraps. Sign-offs and `hist` copies are immutable in the rules; a change after publishing is a new version, never an edit of the old one.
- Kitchen mail (`#/mail`, admin Mail tab): only the head chef's Google account reads `mail`; the sender's phone sees only `mailstat/<id>` (seen, done) by id. The open mail is read once when the book opens on the head chef's device and again after 30 minutes away, like Pings: no listener, no polling. Its popup is appended to `document.body` with `data-ml` clicks; the chef mark's menu (`js/app.js`) uses `data-who`; the page uses `data-p` with `ml-` names. Staff-facing words say "Chef".
- Drinks run (`#/drinks`): each person writes only `drinks/<their id>`. The first PIN goes to "One more thing" (`S.drinkAsk = 'first'`); people who signed up before get the card once (`dkCheck()`, `lk.drink.<id>`). The team's drinks are one query when the page opens, again after 30 minutes: no listener. Clicks use `data-p` with `dk-` names; its classes are `dr-` (`dk-` classes are the landing dockets). The click tests seed a usual drink for Sam, Ann and Bo so the card stays off other pages.
- Kitchen sections: the head chef sets them in the admin People tab (`config/main.kitSecs`, part of the staff draft; the owner's full save keeps them, a sous chef's save never sends them). Staff and leads pick one after their PIN, once a day (`ksCheck()` / `ksOpen()` in `js/prep.js`, `lk.sec.<id>`, one read of `shifts/<today>_<id>`); the head chef and sous chefs get their role by themselves. `mySec()` is the default section for prep lines, Quick add and wastage when the box is left alone; a typed section still wins. A pick holds for that kitchen day only (`ksGet()` checks the date), so everyone is off their section at midnight with nothing to clear. The picker is a bottom sheet appended to `document.body` with `data-ks` clicks and `ks-` classes; the admin block uses `a-ks-` and `ks-` click names. No sections set up means nobody is asked, which keeps the other click tests free of the popup.
- The admin nav (`.a-nav` in `adminHTML()`, `js/prep.js`) sticks to the top and tucks up to its last row while scrolling down. Its "On this page" chips are read from the open page after each draw (`adminJumps()`): the Insights `.a-sh` headings, otherwise each block's first `.label` and its `h3.a-ch-h` headings. Give a new admin block a `.label` (or `h3.a-ch-h`) and it gets a chip; do not add another sticky bar at the top of the admin panel.
- Admin lists that can grow go through `lvHTML()` in `js/prep.js` (search, filter chips, sort, Show more, phone cards). Give each list its own `key`, keep `data-k` names unique (`lv-q:<key>`, `lv-s:<key>`), and use `lvReveal(key)` when a row is added so it is on screen. Do not hand-build a long `<table>` in the admin area.
- Guides keep each PDF page or photo as a picture in its own Firestore record (`guides/<id>/pages/<n>`, under 950 kB, made on the head chef's device), because the free plan has no file storage and a record holds at most 1 MB. The list is read once a day per phone and kept in `lk.guides`; pages are read once per version and then come from Firestore's offline copy. Do not add a listener. A page opened big is appended to `document.body` and its clicks use `data-gz`. pdf.js is loaded from jsDelivr only when a PDF is chosen; the tests serve it from `tests/node_modules/pdfjs-dist`.
- Guides, Shift pings and Meeting minutes can be held back from staff (New pages in the admin People tab, `staffSee` in `config/main`). Any new link, card or read for those pages checks `featOn('guides' | 'pings' | 'minutes')` in `js/prep.js` (`LK_PREP.featOn` in `js/app.js`). It is worked out from the staff list and the person on the phone, kept in `lk.feat`, and `lk-feat` tells `js/app.js` to redraw the menus.
- Double ups on the prep list merge by themselves (`mergeDups()` in `js/prep.js`). It reads the lines from the server first (`getDocFromServer`) and tries each group once per page load: keep both, or a phone with an old copy of the list can remove a line ticked elsewhere, or read again on every redraw. A line with `dupOk` is never merged.
- The service worker opens the book from the saved copy and fetches the newest shell files (`SHELL` in `sw.js`) behind it, all or nothing, then tells the book (`lk-new`, handled in `js/upkeep.js`). A new file the book needs at start goes in `SHELL` and in both file lists in `js/upkeep.js`; those lists fetch with the `X-LK-Fresh` header so the worker goes to the network for them. Bump `CACHE` in `sw.js` when icons or the manifest change.
- The security header in `index.html` lists every outside service the book may load. A new one (a script, a font, an API, a frame) has to be added there or the browser blocks it. Keep scripts in files: inline `<script>` blocks and `onclick=` attributes do not run. In tests use `L.waitFor`, not `page.waitForFunction`, and `L.settle(p, ms)`, not `p.waitForTimeout(ms)` (it stops early once the page is still, but still waits for any timer due in that time). A check on something read from Firestore (a count, a card, a badge) waits for that thing itself with `L.waitFor`; the page can go still before a slow read comes in, and the test then fails only under load.
- Recipe changes from the book (`js/overlay.js`): it must load after `js/data.js` and before `js/prep.js` and `js/app.js` (index.html, and it is in `SHELL` and both `js/upkeep.js` lists). It keeps a clean copy of `js/data.js` and changes `LK_DATA.recipes` and `menuOrder` in place (both files hold on to them). Anything that edits a recipe starts from `LK_RX.pristine(id)` or `LK_RX.change(id)`, never from the object `js/app.js` changed (it adds `contains`, `check` and `sec`, which must not be saved). When new changes arrive, `js/prep.js` clears its recipe caches (`rxReset()`) and fires `lk-rx`; `js/app.js` runs `reindex()`. A new cache built from `D.recipes` in either file must be cleared there too. The changes are read with one read of `book/index` (`rxSync()`), never with a listener.
- Manage Recipes & Drawings (`js/manage.js`, `#/manage`): only the head chef (`LK_PREP.bookEdit()`: their PIN as `headId`, or the Google device with nobody else signed in; `bookEdit()` in `js/app.js` asks it). The menu item and the card's Change this recipe slot (`#r-edit`) redraw on `lk-who`, `lk-admin` and `lk-cfg`. `js/manage.js` is loaded by `mountManage()` in `js/app.js` and is not in `SHELL` or the `js/upkeep.js` lists, so staff phones never fetch it; bump `MG_API` in `js/app.js` and `API` in `js/manage.js` together when what `LK_APP` or `LK_PREP.book()` hands it changes. It draws into its own `#mg-root` (never `#prep-root`, which `js/prep.js` rewrites), clicks use `data-mg`, typing `data-f`, classes `mg-`. A save is one batch through `W()`: `recipes/<id>` (set, never merge), `book/index` (merge, `r.<id>` the same version) and `recipes/<id>/hist/<old v>`; the version is read from the server first. Drafts live in `lk.mg.draft.<id>` until a save is confirmed, and `LK_PREP.unsaved()` asks `LK_MG.dirty()`.
- Drawings made in the book (`js/draw.js`): a recipe points to one with `art`, `side` or `diagram` set to `@<drawing id>`. `js/overlay.js` keeps them in IndexedDB (`lk-book`) and lays them into `LK_ART` under the `@` key (plates and pans with their own viewBox in `LK_ART.vb`); `lk-art` tells `js/app.js` to redraw. Everything from Firestore goes through `LK_RX.clean()` first (plain shapes and text only); keep it that way for any new field that is drawn. The servingware is wrapped in `data-surf` so `foodMask()` leaves it out. A library piece's drawing never changes under a saved drawing: `defs` keeps a copy, and an item's `v` in `js/lib/` goes up whenever its drawing changes. Library items must pass `node tests/library-check.js` (plain SVG, no ids, seeded random only, unique ids, the metadata `js/smart.js` relies on: role, g or n, form, side). Clicks use `data-dw`, typing `data-dwf`, classes `dw-`; the editor draws into `#mg-root`, and `js/manage.js` does not draw while it is open. A plate or pan drawing's save also writes the recipe (`LK_MG.patchRecipe()`): the Pass labels are made from the parts (`ing`, plus the ingredients drawn inside a part in `also`, names joined with `|`, their list places in `ai`), except labels marked `own`.
- Reuse (`js/draw.js`, 21 Oct 2026): templates are `drawtpl/<id>`, the head chef's own pieces and servingware `drawlib/<id>` (type item or surf); the editor reads both with one query each when a drawing opens (`loadMine()`), cleans them with `LK_RX.clean()` and hands the pieces and servingware to `LK_LIB.mine()`. A part that is not a library piece is `t: 'raw'` (`a: raw:<key>`, its drawing in `defs`, `bx` its box): anything that walks the parts uses `isPiece(el)` (item or raw), not `el.t === 'item'`, unless it needs the library item itself. A new drawing can start from `#/manage/draw/new/<recipe>/<slot>/<book:key|tpl:id|d:drawing id>`; copies never write to what they came from. New collections need their rules, the Backup and nightly backup, and `movePin()`.
- Draw it for me (`js/smart.js`): plain rules on the device, no AI service and no new reads beyond one `getDoc` of `book/matches` when the editor opens (and one of the plate drawing when a side view is drawn). It plugs into `js/draw.js` only through `smart('tools')`, `smart('panel')`, `LK_SMART.ui.cmd`, `LK_SMART.match`, `teach` and `pendingOps()` (the picks ride in the drawing's save batch). The same recipe and seed must give the same drawing: use `LIB.P.rng`, never `Math.random`. Keep the matcher at 85% or more on the book's dishes (`node tests/smart-match.js`); a new library piece with a clear name and search words is the usual fix for a miss. The side view's labels go above each part (`labelAbove()` in `js/draw.js`), like the book's own side views; the plain side shapes are `side-profile-<side.s>` in `js/lib/build.js`.
- Drawn from the recipe (`js/compose.js`, 21 Oct 2026): an ingredient with its own card is drawn from that card (`partFor()`, asked first by `partsOf()` in `js/smart.js` and by the ingredient chips in `js/draw.js`). The part is `t: 'raw'` with `role`, `made` (the card's id) and `ms` (the card's signature, so a changed card can be found later); anything that walks the parts uses `itemOfEl()` in `js/smart.js` or `isPiece()` in `js/draw.js`, not `el.t === 'item'`. Every drawing it makes goes through `finish()` (fills snapped to the book's palette from `LK_ART`, outlines made again), so keep new drawings on `ST.edge`, `ST.lift` and the `BIT` shapes, and keep `node tests/style-check.js` clean (outlines at 0.74 of the fill, 90% or more of fills the book's own colours). The colours of raw ingredients are in `RAW`, taken from `js/art.js`; a new ingredient that shows in a mix needs a line there. A new card reading belongs in `EXPECT` in `tests/compose-read.js`.
- One clock: anything saved, or compared with a saved time, uses `now()` in `js/prep.js` (`LK_TIME.now()` elsewhere), and today's date, hours and weekdays use `dayNow()` and `T.day`, `T.hour`, `T.mins`, `T.dow`, `T.clock`, `T.at` (kitchen time, Queensland). Never `new Date()` or `Date.now()` for those: the phone's clock and zone can be wrong. `Date.now()` is only for time passing on the phone (timers, the PIN lock, the idle sign-out). Do not name a local variable `now` or `dayNow`, it hides the helper.
