# Supplier order and catalogue (24 Oct 2026)

Moved here word for word from `README.md` on 12 Nov 2026, so the README stays short enough to read. `README.md` keeps a short summary under the same heading.

**Chef hat > Supplier order** (`#/suppliers`) is for the head chef, sous chefs and the verified admin. Staff, leads and function managers cannot open it or read its data. It is lazy-loaded, uses the current Kitchen Book fonts and controls, and has a collapsible supplier sidebar. The selected supplier shows current pars, exact source names, pack details and quantities from its last recorded order, with weekday and time in Queensland.

**Catalogue:** Admin > Content > Suppliers & pars opens the same editor as Manage catalogue in Supplier order. Only the head chef (their own PIN) or the verified admin edits it. The full admin panel needs verified owner Google authentication, the current head-chef PIN session and its matching device grant. Edit current pars, add manual items, keep source records, set units and verified pack conversions, add confirmed matching names, archive or restore. Blank pars and zero are different. Saved changes have a revision and audit entry; a stale version never silently overwrites another device. Imported product names and original pars stay unchanged. Discontinued items are archived, not deleted.

**Private import:** the editor accepts a checked version-1 JSON catalogue, previews its suppliers, item sequence and count, and asks which existing reminder each supplier belongs to. Supplier goods and source documents are never public assets. The private import file is supplied separately. Existing IDs follow file order, new IDs are inserted once in their file positions and retained extras follow; reimporting preserves live edited pars and manual additions. No-op imports do not create revisions. An explicit supplier split archives original moved items and saves both catalogue revisions and audits atomically. An absent destination ID can resolve to one exact existing supplier name. Complete original-name and pack matches retain that destination's raw item maps and IDs; other moved items keep their original IDs and details. Its immutable history link and item map preserve earlier quantities alongside its own orders without rewriting them. Choose separate existing reminders; no delivery dates are invented. Current drafts follow the same item mapping after confirmation, and a draft conflict stops the split. If an import stops part way, the page names how many suppliers were saved and keeps the remaining plan. No-op and error feedback stay in the review frame.

**Orders:** enter a number, review, then Record order placed after placing the actual order with the supplier. A number uses the configured order unit when one is shown. With no configured unit it still saves, shown as e.g. 2 (unit not set); explicit entries such as 2 kg continue to work. Stock counts also accept numbers, including zero. Unit-dependent top-ups stay off until units and any conversion are confirmed. Catalogue changes preserve the meaning of existing draft quantities, and old history never gains a unit retroactively. This sends nothing to a supplier. An immutable snapshot keeps names, quantities, packs, pars, source, writer and time. The same transaction saves its linked cut-off occurrence and the existing Ordered tick. A retry keeps its order ID; another chef's order asks for an explicit Additional order. A supplier ticked on the order list first (no quantities) is not an order yet: its sheet records the quantities with a plain Review (5 Nov 2026, before this Review stopped with "already marked" and Try again went round in a loop). Copy and Use quantities only fill a draft. Each item's Last order column keeps its latest purchase quantity and date from the loaded history, including when the latest batch omits it. Supplier selection loads 20 recent orders; Older orders extends coverage on demand. Unchecked earlier history is labelled explicitly. The latest-order header, Suggestions and reuse still describe the whole saved batch.

**Existing reminders:** a supplier name on the cut-off bar or tick list opens its sheet; phone pushes include a validated local supplier/cut-off link. A cut-off with no catalogue supplier, or more than one, opens a short card instead (27 Oct 2026): "Valley Veg is not in the supplier catalogue", when it closes, whether it is done, and the Order list. It never opens another supplier's sheet and reads no order history. The head chef sees where to link it (Supplier settings); Refresh opens the sheet once one supplier is linked. **Shared request list** (chosen C, 9 Nov 2026): today's chef list is flat, with Out items first, then older requests by source day and the remaining lines by creation time. A compact **Supplier cut-offs** disclosure shows the nearest unconfirmed deadline and any overdue count. **View / Hide** reveals all existing supplier confirmations and tomorrow's early-order actions. Requests are never assigned by catalogue name, and Orders makes no catalogue read. Staff keep their existing plain list and permissions. `tests/supplier-groups.test.js`. **A supplier's order is ticked on the Order list only** (head chef, 5 Nov 2026): its tick confirms an order placed elsewhere without asking for quantities or units, including for linked suppliers. It saves only the existing shared completion tick, writer and time, and offers Undo; unticking reopens the reminder without deleting history. No catalogue read is needed, no empty order is invented, and detailed drafts, stock counts and previous quantities stay intact. The cut-off bar, Chef to-do and the card show whether it is done, with no tick; the supplier's name opens its detailed order. (Until then the bar's Order done did this, and the tick list opened a linked supplier's sheet.) A failed completion restores the reminder; a queued offline save is not announced as confirmed before the server accepts it. The staff free-text Order list and its item ticks continue as before.

**Order rows (design A, step 2, 3 Nov 2026):** each row has **On hand** next to **To order**, so counting no longer needs Details. A count below par in confirmed units shows **Top up 7 kg · Use** on that row; Use fills only that row, and typing a quantity hides the chip. **−** and **+** sit around To order where the order unit is confirmed; a number moves by one and a typed unit stays. Filter chips: All, Below par, Asked for (once the requests are read) and In this order. **Show what staff asked for** reads today's staff Order list once and lists each matched request with its amount, who asked and when; nothing is ticked off. The draft count and **Review order** stay in a bar above the bottom tabs while the list scrolls. Since 4 Nov 2026 the order sheet is **one list** with no pages: a chip per category jumps to its heading, and typing in On hand, Use, − and + change only their own row, so a 300-item supplier stays quick (about 45 ms a keystroke on a phone-speed CPU, against 79 ms with the old pages of 20). Manage catalogue keeps its pages. On a phone or tablet (under 900 px, 4 Nov 2026) the sheet is **list first**, the Prep list's rule from the work pages design: the heading is one line, the supplier picker and search sit side by side, the cut-off and the last order fold into one tappable line (it opens by itself when an order is already marked placed or the last order could not be read), **Staff requests** is a chip in the filter row, and Suggestions and the help text sit below the list. The first To order box went from 1,284 px down to 656 px on a 390 by 844 phone, clear of the Review bar. Laptops keep everything open.

**Sending (step 3, 3 Nov 2026):** the supplier list shows today's cut-off beside each supplier ("by 15:00", or "ordered" once ticked). Review spells out the order: **1. Send it your usual way** (**Share order text** opens the phone's own text, email or chat apps where the phone offers it, and **Copy order text** is always there), then **2. Then record it here** with Record order placed. The book still sends nothing itself.

**Suggestions:** show why, then Apply. Repeat previous quantities, use a fresh counted-stock top-up with confirmed units/conversion, or flag an exact product name/confirmed alias from the staff Order list. Ambiguous requests stay unmatched; supplier orders do not tick staff requests automatically. No guessed consumption, automatic orders or automatic par changes. Suggestions never overwrite typed quantities.

**Signal, privacy and saved work:** private catalogue/history use Firestore Lite on the existing Firebase app, without a persistent catalogue cache. They need a connection. Drafts are held in memory for the current signed-in session; signing out or changing the person clears them. Save errors retain inputs. A timed-out save is unconfirmed: check the latest history or catalogue before retrying. No signal or a refused read is never treated as an empty catalogue. A saved supplier that fails the catalogue check no longer hides the others (5 Nov 2026): Supplier order opens with the rest and a card names the one that could not be read and its first bad item; any other failure shows its error code after "Could not finish". Missing module, mismatched API and unpublished rules have retry/access messages. Other kitchen pages retain their current offline behaviour.

**Reads and data:** catalogue is one query on entry or Refresh (one read per supplier). An acknowledged catalogue change also invalidates the Orders grouping cache, read again on its next use; recording an order does not. History/audit use bounded queries with one extra document to detect continuation, never per-item reads or polling. An ordinary supplier's 20-order page costs at most 21 order reads. A split merges its own orders with bounded original history through the fixed split timestamp, at most two queries and 42 order reads per page. Independent emitted-document cursors advance on Older orders; exhausted streams need no further query. First attachment, including an existing unlinked destination, adds one latest-original-order query, at most two documents. Records are `suppliers/<id>` with optional immutable `historyFrom`/`historyBefore` and `historyItems` metadata, its `orders` and `audit` subcollections, and `supplierlinks/<cut-off day>_<cut-off id>`. Older splits without an item map retain identity matching. Existing `cutdone` keeps its old shape. Manual backup, nightly backup and PIN migration preserve the raw records, lineage and complete map. Publish and verify the additive map/first-attachment rules before the dependent client, then verify the canonical foundation and live Lock probe; role access stays unchanged. Retain the mapped split reader and rules for already saved splits during rollback.

`js/supplier-core.js` contains the shared validation, quantity and suggestion maths; `js/supplier-store.js` the online-only client and transactions; `js/suppliers.js` the interface. None belongs in the app's start-up shell. `docs/supplier-workspace.md` is the accepted contract and verification record.

A pre-existing fallback-font problem found by the baseline tests was corrected at the same time: wide top-bar navigation may wrap so Kitchen Book remains on one line at 1280 px when the web font has not loaded.
