# Rules publication

The GitHub **Publish rules** workflow uses `scripts/publish-rules.cjs` with the existing pinned Firebase CLI 13.29.1. The adapter replaces only the release helper; compilation, immutable ruleset upload, canonical preparation, foundation verification and the live Lock probe keep their existing order. It changes no application permissions or stored data shape.

The publisher takes no arguments and permits only this project's default Firestore release. The pinned Firestore consumer supplies `cloud.firestore/(default)` even when the ordinary configuration omits a database field; the adapter accepts that exact alias and `cloud.firestore`, normalising both to the same canonical default release before requests. Named databases, other services, foreign projects and malformed identifiers are refused before activation, with fixed boolean evidence and a safe phase message. Unexpected arguments, an emulator environment, a rules endpoint override or a different CLI version stop it before CLI startup. The workflow still fills the existing temporary template and uses its existing service account. Direct CLI, local shell and console publication are outside this adapter.

Each publication sends one release PATCH. An ordinary HTTP 200 with the expected release name keeps the pinned CLI's acknowledgment contract. An actual HTTP 404 from PATCH permits one CREATE. The pinned CLI supplies a default status 500 for some transport errors, so the adapter requires the real response context before treating an error as 404. Other definite 4xx responses, except an ambiguous request timeout, retain the original error and stop. A refused CREATE, including 409, retains both the original PATCH and the create failure.

**An uncertain ruleset upload (13 Nov 2026).** Publishing #688 got `HTTP Error: 503, The service is currently unavailable` at the ruleset upload seven times in a row (01:29 to 02:06 Queensland time), from the branch and from `main`, while the compile check passed every time. A read-only count showed each of those rulesets was stored all the same: the newest was made the second the last 503 came back. The project held 93 rulesets, far under Firebase's 2,500. The CLI stopped at the 503, so the release never moved. The adapter now handles an uncertain upload (no HTTP answer, 408 or 5xx) the way it handles an uncertain release: it reads the stored rulesets once (the CLI's own list and content reads), accepts one only if it was made in the last 15 minutes and holds exactly the files sent, and otherwise keeps the original error. It never repeats the upload. Its evidence line (`Ruleset upload evidence`) is booleans and counts only, and appears only on that path. `scripts/rules-publisher-check.cjs` covers a matching, a different, an old and a foreign ruleset, a refused list and a definite refusal.

Transport failures, HTTP 408/5xx and invalid returned release names have an uncertain outcome. On those paths only, the adapter reads the exact default release at most twice. Both responses must name the intended immutable ruleset before activation is accepted. A missing, malformed, changed or different pointer, or a refused read, fails publication. The reads have 15-second deadlines and reject redirects. There is no polling, mutation retry, release deletion, content-only shortcut or IAM change. These observations establish activation at the time of the checks; another authorised publisher can change it later.

The fixed activation report contains status codes and booleans. It distinguishes a successful PATCH from confirmed activation after an ambiguous failure. Composite errors display fixed phase/status summaries and retain the original errors in memory; they do not print arbitrary API bodies through those summaries. Foundation verification and the live Lock probe remain separate required gates.

Run `node scripts/rules-publisher-check.cjs` after installing `tests/rules` dependencies. It uses synthetic responses and transport stubs, including the actual pinned Firestore prepare/deploy/release pipeline, without credentials or network requests. Ordinary and explicit-default configuration exercise existing-ruleset reuse, upload and confirmed ambiguous activation; named database activation remains refused. It also proves the old unconditional CREATE after PATCH 403, then checks the corrected refusal, response provenance, pointer mismatch, error preservation, safe composite logging and invocation guards. The required CI processing stage keeps all eight existing checks and runs this ninth check after dependency installation; browser tests do not load Firebase CLI modules.

**What the published compiler refused that the emulator accepted (4 Nov 2026).** Publishing the Change amount rules (#525) failed four times at the compile check with `HTTP Error: 503, The service is currently unavailable`, while the same workflow from `main` compiled, published and passed the Lock probe in between. Taking out a non-ASCII character in a comment and a top-level `? :` did not help. What did: the unit list was passed into a function (`amountChange(units)`, then `d.unit in units`); with the list written out where the function is called, the file compiled at once. The upload that followed got one 503 too and went through on a re-run. So: write a list used with `in` where it is checked, not as a function parameter; keep `firestore.rules` plain ASCII anyway (`grep -P '[^\x00-\x7F]' firestore.rules` finds none). A 503 at the compile check that repeats while `main` compiles is the file, not Google: compare it with `main` before waiting. A single 503 at upload or release is worth one re-run. On 7 Nov 2026 it went the other way: the compile check gave 503 twice in a row on a file whose only difference from `main`'s published rules (a 7-line read rule) had compiled that afternoon, and the third try 12 minutes later went through. So compare with `main` first; when the difference has compiled before, wait about 10 minutes and run once more before changing the file.
