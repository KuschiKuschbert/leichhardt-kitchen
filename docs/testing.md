The `tests/` folder holds click tests that open the book in Chrome and use it like the team does, on a phone, a tablet and a computer. Only the tests need installing (Node.js and Google Chrome on the computer):

```

```

- **Focused checks.** From `tests/`, `npm test -- recipes lists` runs files whose names contain either substring. `npm test` without filters still runs every `*.test.js` file. If none of the supplied filters matches a file, the command exits 1 with the filters and a useful next step, before opening the server or Chrome. `tests/runner-selection.test.js` checks that rejection with an occupied server port and an unavailable Chrome executable; it failed 6 of 8 assertions before the fix and passes all 8 after it.
- **JavaScript parsing.** The workflow loop includes `node --check "$f" || exit 1`, making the snippet stop explicitly without relying on inherited shell options. `tests/syntax-gate.test.js` extracts that loop and runs four temporary root/library/service-worker cases in standalone Bash with `errexit` off. Two of four cases failed before the guard and all four pass after it. The recorded GitHub step used Bash `-e`, which already stopped on an early parse failure; these fixture results establish portable snippet behaviour, not an observed GitHub acceptance of invalid JavaScript.
- **A failure stops in seconds** (4 Nov 2026). Every file connects to the run's one Chrome, and that open connection keeps node running. So a file ends `})().catch(e => { console.error(e); process.exit(1); });`, never only `process.exitCode = 1`: with that, a 5 second `waitFor` failure sat until the 600 s `FILE_TIMEOUT`. `tests/exit-on-error.test.js` reads every test file and fails on a top-level catch without `process.exit`. It flagged 16 files on the old `main`.

The tests do not sit out fixed pauses (21 Oct 2026): `L.settle(p, ms)` waits at most `ms` but stops as soon as the page has gone still, nothing is loading and no timer is due inside those `ms`, and `L.open` also waits for the kitchen's settings to be read. A click or wait that has not worked in 10 s fails (Playwright's own limit is 30 s). The whole run went from about 3.6 minutes to 1.4 on a four-processor computer. For something that comes in later than the page goes still, wait for the thing itself with `L.waitFor`. Each file's output prints in one piece when it ends, with its time, and the five slowest files are listed at the end.

- **On GitHub.** The same tests run on every pull request to `main` as the **Click tests** check (`.github/workflows/pr-tests.yml`, Chrome on the runner, screenshots kept as an artifact when a run fails), so a pull request cannot merge until they pass. Since 22 Oct 2026 the same check also runs `node --check` on `js/lib/*.js`, the rules checks on the Firestore emulator (`tests/rules`) and the nightly learning check (`scripts/emulator-check.mjs`), so a rules change cannot merge without them. After each Pages deploy the **Live click tests** workflow runs them again against the live site. A pull request that changes only Markdown files or files under `docs/` passes the check in about a minute: the step "Is this pull request docs only?" lists the changed files (renames as both names) and skips the browser, rules and emulator steps (3 Nov 2026). Any other file, and every run by hand, runs it all. The browser files run in five shares of equal work on five runners at once (`SHARD=k/5`, by the seconds in `tests/timings.json`, longest first; `offline-writes` runs in three parts beside itself), beside the rules checks, and the job named **Click tests** passes when every part did. In those runs a passing file prints one line (`QUIET=1`), a file still running after 10 minutes is stopped and counted as failed (`FILE_TIMEOUT=600`), a failed file runs once more on its own (`RETRY=1`, a warning when it then passes), and the failures go into the run summary and annotations. The Live click tests use the same five shares.
