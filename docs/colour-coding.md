# Colour coding across the Kitchen Book

9 November 2026. Chosen scope: consolidate operational state colours within the existing design. The head chef asked the independent council to decide whether shared colour meanings would improve readability and authorised the resulting focused pass. This follows the whole-app audit council in [whole-app-audit.md, section 5](whole-app-audit.md#5-run-an-independent-critical-council). It introduces no new layout, navigation or service step.

Source baseline: `72d36a0`, current main when the audit began. Status: the focused CSS implementation and local verification are complete; required CI and the normal release queue remain the release gate. No live operational records were read or written for this audit. The review is role-based analysis, not research with kitchen staff.

## What the council decided

All five independent reviewers support a focused pass. None supports a wholesale recolour.

| Reviewer | Independent verdict | Main condition |
| --- | --- | --- |
| Kitchen operations and product | Repair readability, consolidate implementation, preserve established meanings. | Claimed Prep work must stay readable. Keep named Urgent, category colours and familiar work-page treatment. |
| Visual design and accessibility | Consolidate semantic colours and repair contrast. No layout or flow changes justified. | Use readable text variants on each surface. Preserve words, checkmarks, focus and other non-colour cues. |
| Usability and information architecture | Consolidate operational status colours, with explicit exceptions. | The next action, pending work, completion and errors must remain distinguishable in words. |
| Architecture and performance | Consolidate implementation and repair contrast, preserving approved layouts and colour roles. | Reuse shared tokens. Add no reads, rules, listeners, dependencies or parallel state model. |
| Quality and release engineering | Consolidate implementation and repair verified readability failures. Preserve existing meanings, artwork and approved page designs. | Use computed-style and journey checks. Keep source review, mocked browser checks and live behaviour separate. |

Disagreement: the visual reviewer suggested changing blue New and Moved function tags to orange. The chosen scope preserves these category distinctions. Their labels describe kinds of change, not a shared failure or success state. The usability reviewer suggested a visible 2h/4h label on the mobile completed clock. That changes the separately approved timer presentation and is deferred. This pass may repair its state colours without changing stages, labels, timing or controls.

The service benefit is a stable meaning for completed work, attention and failure when staff move between pages. The colours reinforce existing labels. They do not establish whether a write succeeded, whether someone is available or whether food is safe.

## Shared meanings

| Meaning | Tokens and treatment | Boundaries |
| --- | --- | --- |
| Ordinary content and neutral context | `--ink`, `--muted`, `--faint`, paper and divider tokens | Quiet text still needs contrast. A disabled control is a separate state from an unreadable row. |
| Action, active choice and attention | Existing orange: `--accent`, `--accent-ink`, `--small-ink`, `--tag`, `--hit`; `--bar-accent` on charcoal | Orange is also the book's brand and heading colour. Do not interpret every orange word as overdue. Keep the more readable small-text variant. |
| Urgent Prep work | Existing charcoal Urgent badge, selected control and row edge | Preserve the established word and treatment. Charcoal selection elsewhere is also valid when pressed/current state is explicit. |
| Complete, saved, included or assigned | `--done`, `--done-ink`, `--done-tint`; `--done-on-dark: #9FE0B7` on charcoal | Use `--done-ink` for small text and filled labels, with `--done` retained for appropriate decorative frames. Assigned in a Team draft does not mean Saved. A new unsent line must not look completed. |
| Failure, invalid input, destructive action or an explicitly adverse state | `--bad-ink: #9B2716`, `--bad-tint: #FBE9E5`; `--bad-on-dark: #FF9C8A` on charcoal | Reuse the existing dashboard red as the shared source. Preserve Error, Try again, Cancel function, Delete and other outcome words. Red does not replace the second-tap or existing confirmation behaviour. |
| Waiting or not sent | Existing neutral/orange pending treatment plus explicit words | Pending is not a confirmed failure or success. Preserve acknowledgement timing and retry rules. |
| Categories, quantities, art and surface identity | Existing local palettes and legends | Wastage reasons, chart series, heat scales, allergens, drawing colours, festivals and approved Home surfaces are not generic state colours. |

The same meaning may need a different foreground on warm paper and charcoal. Sharing a semantic token is preferable to repeating its hex. Do not replace every local colour with one universal swatch.

Quiet secondary actions can stay neutral. The shared `.p-x` class includes Remove, Put back and other ordinary actions, so it is not globally red. Use the failure family where an existing dedicated destructive or adverse-state style supplies a colour cue.

## Findings and acceptance

| ID | Expected and source finding | Decision, risk and verification |
| --- | --- | --- |
| COL-01 | The same failure reads differently across pages: `.p-err`, cleaning errors and several editors use orange, while function validation and dashboard adverse states use several red literals. | Consolidate failure/invalid/destructive colours around the existing dashboard red and its readable dark variant. Medium visual risk because shared selectors have many consumers. Check computed foreground/background and representative acknowledged save, pending and failure states. |
| COL-02 | Small text on warm paper and status text on charcoal need distinct readable variants. Existing `--accent-ink` is not suitable for every small-text/surface pair. | Repair identified contrast failures, including nested text inside function status strips. Check actual computed colours and font size/weight. Do not infer a whole-app WCAG pass from a token calculation. |
| COL-03 | A Prep line claimed by another cook uses whole-row `opacity: .55`, including its work and metadata. The row remains actionable for takeover. | Restore readable work text while retaining the existing claimant cue. High service value, small reversible CSS change. Check readability, ownership distinction, unchanged row dimensions and the takeover journey. |
| COL-04 | Completed work already uses green, but filled ticks, fine text and decorative frames use different variants. | Preserve justified variants and consolidate duplicated values by role. Keep Team draft assignment and Drinks participation wording. Check labels/pressed states and server-acknowledged Saved separately. |
| COL-05 | Similar hues also encode categories, measures and art. Replacing them as generic statuses would remove information. | Preserve the exceptions in the inventory. Compare representative Wastage legends, chart series, heat cells, allergen tags, function categories, Home surfaces, drawings and celebrations. |

Acceptance for this pass:

- Orange remains action/selection/attention; charcoal Prep Urgent remains familiar; green remains completion or explicit inclusion; red consistently marks failure, invalid/destructive or existing adverse states.
- Pending, saved, failed and draft states remain explicit in words. No colour change creates a new acknowledgement or changes permissions, booking state, assignment, food guidance or stored data.
- Layout, spacing, target sizes, list row heights, visible lines, routes and action counts remain unchanged. No new controls, tabs, overlays, fields or service steps.
- No extra reads, writes, rules, listeners, dependencies or runtime state. Category, artwork, chart and print meanings stay intact.
- Verify relevant text contrast at 4.5:1, large text at 3:1 and meaningful control/state boundaries at 3:1 where applicable, against the actual surface and opacity. Preserve non-colour cues and existing keyboard/focus behaviour.
- Run the focused contrast, screen-reader, design-pattern and affected journey checks, followed by the repository's required broader gate. Check representative pages at 390, 768 and 1280 px, including charcoal boards, large text, pending and failure states.

## Release and rollback

Ship as one focused, reversible visual change under the existing branch, PR and saved-shell rules. Keep the operational code, state timing and Firestore rules unchanged. Stop release for unreadable labels, a missed pending/error state, a category recoloured as a verdict, changed list geometry or a failed critical journey.

Rollback is a revert of this pass's CSS and related documentation/tests through a fresh branch and PR. No data migration or data rollback is needed. Keep the previous working palette available in Git and verify the known-good app revision after redeployment. Do not revert unrelated timer, Home, security or saved-shell work.
