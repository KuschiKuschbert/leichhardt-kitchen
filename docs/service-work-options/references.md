## Timer scope and earlier food-safety research

The owner clarified that the feature is shared clock timers: one-action 2-hour/4-hour presets, optional names and the existing chime repeating at expiry until any signed-in kitchen staff member marks Done. Any kitchen staff member may start or stop them, including those with Add/Tick disabled. There is no temperature, stage, procedure-approval or food-safety-record workflow. This explicit timer-only exception does not grant other rights.

**Verified source:** `js/chime.js` exposes `list`, `first`, `has`, `play` and `wake`. Its `timer` ID is the existing Oven timer sound. There is no loop/cancel API and `play()` confirms an attempt only. The proposed repeat cadence is **[15 seconds]**, coalescing due timers with one sound leader per device across tabs. Recheck current timer state after asynchronous audio resume and before sound creation to avoid a late burst after another device marks Done. An already sounding short burst may finish. Reuse this module, with no new audio service. `config/main.pingSound` remains the separate Shift pings policy, including Off; timer control does not grant access to it. The timer information page needs only explanation and Test chime.

Earlier research inspected [FSANZ cooling and reheating guidance](https://www.foodstandards.gov.au/business/food-safety/cooling-and-reheating-food) and its separate [2-hour/4-hour rule](https://www.foodstandards.gov.au/business/food-safety/2-hour-4-hour-rule). These remain external context only. They do not impose fields, stages or an activation gate on the clarified timer feature. Done acknowledges the timer and ends ringing; it claims no food-safety result. The earlier proposal for recorded cooling outcomes is superseded.

## Browser and notification evidence

**Verified:** [MDN setTimeout](https://developer.mozilla.org/en-US/docs/Web/API/Window/setTimeout) explains background throttling and late execution. Chrome can check timers only once per minute under intensive throttling; Android Firefox may unload inactive pages. A countdown is therefore a view of an absolute deadline, not a trustworthy background scheduler.

**Verified:** [MDN Notifications usage](https://developer.mozilla.org/en-US/docs/Web/API/Notifications_API/Using_the_Notifications_API) requires permission, recommends requesting it only from a user action and notes secure-context requirements. Permission can remain default, be granted or be denied. Desktop Notification construction is not portable to mobile; a service worker’s showNotification is the appropriate mobile mechanism. This displays a notification when code runs, not a guaranteed future alarm.

**Verified:** [MDN Push API](https://developer.mozilla.org/en-US/docs/Web/API/Push_API) describes server-delivered messages when the app is not loaded, requiring an active service worker and push subscription. [WebKit iOS/iPadOS Web Push](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/) documents Home Screen web-app support from 16.4, permission from a direct user interaction, lock-screen delivery and Focus controls. Actual support must still be tested on the venue’s current devices.

| Closed browser/app | No local countdown-based alarm promise. | Close and reopen; shared end unchanged, expired timer visible and unlocked foreground chime resumes until Done. |
| Audio blocked / gesture needed | Persistent expired state and Test chime; local chimes need no notification permission. | User gesture, silent mode, interrupted audio and wake; no claim that API return proves audibility. |
| Poor connectivity | Confirmed end time stays stored in Firestore; pending Start/Stop/Done is named. An offline reload does not promise kitchen data. | Offline, retry, second device, handover and failed save; another person's confirmed Stop/Done ends ringing on reconciliation. |

The timer feature needs no new push service. Its first-release contract is shared persisted end times, visible expired state and the repeated existing foreground chime until Done where browser audio can run. Existing supplier cut-off push is not a timer delivery service. Hidden screens skip sound and missed bursts; returning screens reconcile and resume with at most one current burst. Prototype sound requires an explicit Test chime or sound-demo gesture. Guaranteed closed-app alarms remain outside the proposal; any later push work would need a separate implementation and physical-device checks.
