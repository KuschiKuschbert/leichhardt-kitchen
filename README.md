## Adding or changing a recipe

The ingredient arrow keeps the related details beside the list on a wide screen and under the row on a smaller one. Amount and ingredient stay in the row. Closing the details keeps the draft for the recipe’s existing Save action. [Recipe editor](docs/recipe-editor-options/brief.md#ingredient-details-beside-the-list-22-november-2026)

All recipes are in **`js/data.js`**. The top of that file explains every field. Recipes the head chef changes or adds in the book itself are kept in Firestore and laid over this file, and the book's copy wins (see Recipes changed in the book below). To add one here:

1. Copy an existing recipe block, from `{` to `},`.
2. Give it a new `id` (short, no spaces, for example `gravy`) and the next card number.
3. Fill in the name, yield, ingredients, steps and allergens.
4. To make an ingredient tappable, add `link: 'gravy'` (the other recipe's `id`).
5. Put anything that isn't confirmed yet in `[square brackets]` so it shows as a placeholder.
6. Allergens: tag each ingredient (`tags: ['Milk', 'Soy?']`) and leave out `contains` and `check`; the book works them out from the tags.
7. If it is a dish on the guest menu, add its `id` to the right section in `menuOrder` at the top of `js/data.js`, in the spot where the menu prints it. A dish left out of `menuOrder` still shows, under "Other dishes". Batch recipes and components are not listed there.
8. Change `updated` at the top of the file to today's date.

Legacy or uncontrolled pages need a safe navigation to adopt a prepared generation. If something changed it tells the open book, which takes it up by the usual rules (since 24 Nov 2026 never part way through a start: it used to reload straight into it within the first 8 seconds after opening; before 13 Nov it showed the "New version available" bar) and updates the same way as before (straight away when brought back, otherwise after 2 minutes untouched, or with Update now). The update and 04:00 refresh retain their guarded worker handshake; explicit retry retires a background round older than eight seconds, and an obsolete round cannot publish. An opening shares a round that is already running only before that round has asked for its files; after that it gets one more round once that one ends (4 Nov 2026). It used to share the round whatever its state, so a version that came out between two quick openings was not found: no `lk-new`, and the book waited for the strip. That was the cause of the flaky "just opened" checks in `tests/saved-copy.test.js`. See [saved-shell generations](docs/saved-shell-generations.md). The pages loaded only when they open (Manage recipes and the drawing editor, Manage functions, Delivery received, Supplier order) load their non-shell scripts with a version (`?v=N`): the worker keeps each under its plain address, one copy per file, network first past the browser's own copy (28 Oct 2026: GitHub Pages lets the browser keep a file for 10 minutes, so after an update a page opened again ran its old scripts, and the worker kept those for no signal), so once a page has opened with signal it opens with no signal too (28 Oct 2026; before, nothing with a `?` was kept, and after the book reloaded those pages said they could not open). Each page checks the version it got (`MG_API`, `FE_API`, `SUP_API` in `js/app.js` and the files' own `API`) and offers Reload the book for a different one. Those numbers stay as they are when a change only adds (the file checks for a new helper before it uses it, and the book checks for what the file added): a phone keeps each page's file for no signal, so a new number shut that page with no signal until it had opened once with signal, and Reload could not help (29 Oct 2026; the `?v=` address can still go up, so a browser with no worker in charge fetches the new file). `tests/saved-copy.test.js` opens Delivery received and the recipe and drawing editors with no signal from files kept before a change. Their helpers with no version (`js/library.js`, `js/lib/*.js`, `js/smart.js`, `js/compose.js`) are first fetched with the `X-LK-Fresh` header, which the worker sends to the network first, past the browser's own copy, and waits for the cache-write attempt before replying. A storage failure can leave the older lazy copy saved even when the network response succeeds. A start file (`SHELL`) asked for with a version is never kept under its plain address, since that would replace the saved shell one file at a time; nothing loads one that way. Staff phones still never fetch `js/manage.js`: it is not in `SHELL`. A new worker saves the shell past the browser's own cache (28 Oct 2026; GitHub Pages lets the browser keep a file for 10 minutes, so an install could save files from before a deploy next to new ones). The worker keeps the book's own files only: nothing from Firestore. Google Fonts and the Firebase files are kept once loaded (see Firebase kept on the phone). Firebase's requests for data (prep list, orders, wastage) are not touched. Since 26 Oct 2026 (#387) Firebase keeps that data, and changes not sent yet, in the tab's memory only (`docs/private-kitchen-access.md`), so with no signal the saved copy opens the book but not the kitchen's data. Startup files, the manifest and shell icons belong in `SHELL` and both workerless fallback lists. Other lazy assets retain their own cache behaviour; changing `CACHE` requires an explicit compatible migration, not a blanket cache reset. `tests/saved-copy.test.js` (its own copy of the test server, with every file held back 4 s, then a changed `js/data.js`; the five pages opened with no signal after a visit and a reload; a changed `js/smart.js` sent slowly; a staff phone with no `js/manage.js`; a new worker with the browser keeping files for 10 minutes, and a deploy within those 10 minutes for `js/smart.js` with `X-LK-Fresh` and `js/manage.js?v=4`, in the separate native HTTP-cache case described below; a start file asked for with a version).

The final saved-copy case uses a separate native HTTP-cache context with 600-second caching and no Playwright routes. Its entry and cached index serve the same marked inert HTML; an assertion checks the bare worker marker and absence of `LK_PREP`/`LK_FN` after controlled navigation. The earlier app cases retain their routed setup.
